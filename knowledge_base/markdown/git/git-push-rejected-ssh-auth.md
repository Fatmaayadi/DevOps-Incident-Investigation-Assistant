# Git push rejected: non-fast-forward, protected branch, or Permission denied (publickey)

## Overview

A failed `git push` has three common families of causes. Each one is recognisable from the message:

1. **Non-fast-forward rejection.** Someone else pushed to the branch, and your local branch does not contain their commits. "Sometimes, Git can't make your change to a remote repository without losing commits. When this happens, your push is refused" [R2]. In Git terms, an update from A to B is a fast-forward "if and only if B is a descendant of A". A non-fast-forward update "will lose history", which is why `git push` refuses it by default [R1].
2. **Rejection by the server.** `remote rejected` means "the remote end refused the update", usually because of a hook or a server-side safety option [R1]. On GitHub, branch protection rules can block force pushes, deletions, or pushes that do not meet requirements such as passing status checks [R3].
3. **Authentication failure over SSH**: `Permission denied (publickey).` The SSH key presented is missing, not loaded, not attached to your account, or the wrong user is used [R4].

## Symptoms

- Non-fast-forward [R2]:

  ```text
  ! [rejected]        main -> main (non-fast-forward)
  error: failed to push some refs to '…'
  To prevent you from losing history, non-fast-forward updates were rejected
  ```

- Server-side refusal: the status `remote rejected` [R1].
- SSH: `Permission denied (publickey).` when pushing, or when testing with `ssh -T` [R4].

## Possible Causes

| Cause | Explanation |
|---|---|
| **Remote branch has new commits** | "If another person has pushed to the same branch as you, Git won't be able to push your changes" [R2] |
| **Local history rewritten** (rebase, amend) after it was pushed | Your branch is no longer a descendant of the remote one, so the update is non-fast-forward [R1] |
| **Protected branch** | By default, a branch protection rule "disables force pushes to the matching branches and prevents the matching branches from being deleted". Other rules can require status checks, for example [R3] |
| **Server hook or safety option** | For example `receive.denyNonFastForwards` on the remote [R1] |
| **Wrong SSH user** | "All connections, including those for remote URLs, must be made as the 'git' user" [R4] |
| **No key loaded in the agent** | `ssh-add -l` prints nothing [R4] |
| **Public key not attached to the GitHub account** | The key's fingerprint is not in the account's SSH keys [R4] |
| **Using `sudo git push`** | `sudo` does not use the SSH keys generated by your user [R4] |

## Investigation Steps

1. **Read the push output**: `[rejected]` (refused by your Git because it is not a fast-forward), `remote rejected` (refused by the server), or `Permission denied (publickey)` (authentication) [R1, R4].
2. **For non-fast-forward**: fetch the remote branch and compare it with your branch, to see the commits you do not have [R2].
3. **For `remote rejected`**: check the branch protection rules or server hooks of the repository [R1, R3].
4. **For SSH**: test the connection with `ssh -T git@github.com`, then in verbose mode `ssh -vT` to see which keys are tried [R4, R5].
5. **Check the loaded keys** with `ssh-add -l -E sha256`, and compare their fingerprints with the keys registered in the account [R4].

## Diagnostic Commands

```shell
# Get the remote state without changing your work, then compare
git fetch origin
git log --oneline main..origin/main     # commits on the remote that you don't have
git log --oneline origin/main..main     # your commits not yet on the remote

# Test SSH authentication to GitHub (must be the "git" user)
ssh -T git@github.com

# Verbose: shows the identity files tried and the result
ssh -vT git@github.com

# Keys currently loaded in the agent, with their SHA256 fingerprints
eval "$(ssh-agent -s)"
ssh-add -l -E sha256

# Remote URL in use (SSH or HTTPS, which user)
git remote -v
```

Sources: `git fetch origin` [R2]; `ssh -T`, `ssh -vT`, `ssh-agent`, `ssh-add -l -E sha256` [R4, R5]. The `git log a..b` comparisons and `git remote -v` are standard Git commands selected by the team.

## Interpretation of Results

| Observation | Meaning | Next step |
|---|---|---|
| `git log main..origin/main` lists commits | The remote has work you do not have [R2] | Integrate it before pushing [R2] |
| `[rejected] … (non-fast-forward)` after a rebase of pushed commits | You rewrote published history [R1] | Prefer not to rewrite shared history; if you must, use `--force-with-lease` (see below) |
| `remote rejected` on `main` | Server rule or protected branch [R1, R3] | Push to a feature branch and open a pull request |
| `ssh -T` answers `Hi USERNAME! You've successfully authenticated…` | SSH authentication works [R4] | The push problem is elsewhere (permissions, branch rules) |
| `ssh -T GITHUB-USERNAME@github.com` gives `Permission denied (publickey).` | Wrong SSH user [R4] | Use `git@github.com` in the remote URL [R4] |
| `ssh-add -l` prints nothing | No key loaded [R4] | Load the key, or generate one and add it to GitHub [R4] |
| The verbose output shows `No more authentication methods to try.` | None of the keys tried was accepted [R4] | Compare fingerprints with the account's keys [R4] |

## Possible Solutions

- **Integrate the remote changes, then push** [R2]:

  ```shell
  git fetch origin
  git merge origin/main      # or: git pull origin main
  git push origin main
  ```

- **Rewritten history on your own branch**: `--force-with-lease` overrides the restriction "if the current value of the remote ref is the expected value", and fails otherwise. It is safer than a plain force push [R1]. Do not force-push shared branches (team recommendation).
- **Protected branch**: follow the repository workflow, for example a pull request with the required checks. Force pushes are blocked by default on protected branches [R3].
- **SSH key**: load your key into the agent; if you have none, generate one and add it to your GitHub account; make sure the remote uses the `git` user [R4].
- **Do not use `sudo` with Git** [R4].

## Prevention

- Fetch and integrate often, and push small changes (team recommendation).
- Use feature branches and pull requests for protected branches [R3].
- Do not rebase commits that others may have based work on (*Pro Git*, "The Perils of Rebasing", PDF p. 106).
- Test SSH access once with `ssh -T git@github.com` after setting up a new machine [R5].
