# HTTP 502 Bad Gateway, 503 Service Unavailable and 504 Gateway Timeout behind a proxy or load balancer

## Overview

These three status codes are almost always returned by an **intermediary**, such as a reverse proxy (nginx), an ingress controller or a cloud load balancer, and not by the application itself. The HTTP specification defines them as follows [R1]:

| Code | Definition (RFC 9110) | Short reading |
|---|---|---|
| **502 Bad Gateway** | "the server, while acting as a gateway or proxy, received an invalid response from an inbound server it accessed while attempting to fulfill the request" | The backend answered badly, or broke the connection |
| **503 Service Unavailable** | "the server is currently unable to handle the request due to a temporary overload or scheduled maintenance" | No backend can take the request right now |
| **504 Gateway Timeout** | "the server, while acting as a gateway or proxy, did not receive a timely response from an upstream server" | The backend was too slow, or unreachable before a timeout |

The diagnosis therefore starts by identifying **which component generated the error** and **which backend it was talking to**. On an AWS Application Load Balancer, for example, errors generated by the load balancer itself increment `HTTPCode_ELB_5XX_Count`. Errors returned by targets increment `HTTPCode_Target_5XX_Count` [R4].

## Symptoms

- Users or monitoring see `502`, `503` or `504` responses, often with a generic error page from the proxy or the load balancer.
- A typical timeline is "502 right after a deployment": the new version is not ready, crashes, or listens on another port (team observation).
- The application's own logs may show **no trace** of the failing requests, because the proxy never got a valid exchange with it (team inference).

## Possible Causes

**502 Bad Gateway.** Causes documented for AWS Application Load Balancers [R4]:

- the load balancer received a TCP RST from the target when opening the connection (nothing listening: see `md-net-connection-refused-timeout`);
- the target closed the connection with RST or FIN while a request was in progress. AWS advises checking "whether the keep-alive duration of the target is shorter than the idle timeout value of the load balancer";
- the target response is malformed, has invalid headers, or has a header larger than 32 K;
- an SSL handshake error happened when connecting to the target;
- the deregistration delay elapsed while a deregistered target was still handling a request.

**503 Service Unavailable.**

- On an ALB, the target group has no registered targets, or all registered targets are in an unused state [R4].
- Targets failing health checks are not in service until they pass one health check [R4].
- On nginx, a server that fails `max_fails` times within `fail_timeout` is considered unavailable for `fail_timeout` [R3].
- A temporary overload or a planned maintenance [R1].

**504 Gateway Timeout.**

- The proxy could not connect to the backend in time. AWS ALB uses a 10-second connection timeout; nginx uses `proxy_connect_timeout`, 60 s by default [R2, R4].
- The backend accepted the connection but did not respond in time: the ALB idle timeout, or `proxy_read_timeout` in nginx (60 s by default, "between two successive read operations") [R2, R4].
- A network ACL blocks the return traffic from the targets to the load balancer on ephemeral ports (1024-65535) [R4].
- The target announces a `Content-Length` larger than the body it sends [R4].

## Investigation Steps

1. **Identify who returned the error**: proxy, ingress, load balancer or application. On AWS, compare `HTTPCode_ELB_5XX_Count` with `HTTPCode_Target_5XX_Count` [R4].
2. **Find the backend** that the failing requests were sent to: upstream address, target group, Service (team recommendation).
3. **Call the backend directly**, bypassing the proxy, from the proxy's network location. Use the backend's port and path (team recommendation; see `md-net-connection-refused-timeout`).
4. **For 502**, check that the backend is running, listens on the configured port, and does not close idle connections before the proxy does [R4].
5. **For 503**, check the backend pool: registered targets, health check status, and the security groups and network ACLs used by health checks [R4].
6. **For 504**, measure the backend response time. Compare it with the proxy's connect and read timeouts, and check the network path back from the backend [R2, R4].
7. **Read the proxy logs and the load balancer access logs.** On an ALB, the `request_processing_time` and `target_processing_time` fields of the access logs help locate slowness [R4].
8. **After a deployment**, compare the new version's port, readiness and startup time with the previous one (team recommendation).

## Diagnostic Commands

```shell
# Reproduce and see exactly which component answers (headers, status, timing)
curl -sv -o /dev/null https://app.example.com/health

# Call the backend directly from the proxy host (bypass the proxy)
curl -sv --connect-timeout 5 http://10.0.2.15:8080/health

# On the proxy (nginx): check configuration syntax, then read the error log
nginx -t
tail -n 100 <path-set-by-error_log>

# Kubernetes behind an ingress: are there Ready endpoints for the Service?
kubectl get endpointslices -n <namespace> -l kubernetes.io/service-name=<service>
```

`nginx -t` tests the configuration: nginx "checks the configuration for correct syntax, and then tries to open files referred in the configuration" [R5]. The error log location is set by the `error_log` directive (default `logs/error.log`, relative to the nginx installation prefix; Linux packages often configure another path) [R6]. The `curl` calls are team-selected checks supporting [R2, R4]. The Kubernetes command comes from the official *Debug Services* guide (see `md-k8s-service-no-endpoints`).

## Interpretation of Results

| Observation | Meaning | Next step |
|---|---|---|
| The direct call to the backend is refused | Nothing listens on the backend port: typical 502 cause [R4] | Fix the backend process or its port |
| The direct call works, but the 502 is intermittent | Connections closed by the backend during requests; check keep-alive vs idle timeout [R4] | Make the backend keep-alive longer than the proxy/LB idle timeout [R4] |
| The direct call takes longer than the proxy read timeout | 504 caused by a slow backend [R2, R4] | Optimize the backend, or raise the timeout deliberately |
| The direct call hangs during connection | Network filtering or wrong address [R4] | Check security groups, network ACLs, routing |
| ALB target group has no healthy targets | 503 [R4] | Fix health checks, registration, security groups |
| Only `HTTPCode_Target_5XX_Count` increases | The application itself returns 5xx; the LB just forwards them [R4] | Investigate the application logs |
| Kubernetes Service has no Ready endpoints | The ingress has nowhere to send traffic | See `md-k8s-service-no-endpoints` |

## Possible Solutions

- **Backend down or on the wrong port**: restart or fix it; check the deployment's port configuration (see `md-k8s-crashloopbackoff` if the Pods restart).
- **Connection closed mid-request**: set the backend keep-alive timeout longer than the load balancer idle timeout [R4].
- **No healthy targets**: make the health check path and port correct, and allow health check traffic in the target's security group from the load balancer [R4].
- **Slow backend**: fix the slowness first. Only then, if long requests are legitimate, increase `proxy_read_timeout` (nginx) or the load balancer idle timeout [R2, R4].
- **Deregistration during deployments**: increase the deregistration delay so that long requests can complete [R4].
- **Network ACLs**: allow return traffic on ephemeral ports 1024-65535 [R4].

## Prevention

- Use health checks and readiness checks so that traffic only reaches backends that are ready [R4].
- Roll out new versions gradually, and make sure that old instances finish their requests (deregistration delay) [R4].
- Monitor load-balancer-generated and target-generated errors separately [R4].
- Align timeouts along the chain (client → proxy → backend), and document them (team recommendation).
